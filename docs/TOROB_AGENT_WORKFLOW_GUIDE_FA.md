# راهنمای کار با فایل `Torob_InPerson_Shopping_Agent_Project_Plan_EN.md`

این راهنما روش استفاده از فایل برنامه پروژه ترب را توضیح می‌دهد. فایل انگلیسی، مرجع اصلی تسک‌های پیاده‌سازی است؛ این فایل راهنما روش کار تیم و Agentها را مشخص می‌کند.

## ۱. فایل‌ها را در مخزن قرار دهید

در ریشه ریپوی Git این فایل‌ها را قرار دهید:

- `Torob_InPerson_Shopping_Agent_Project_Plan_EN.md` — مرجع اصلی پروژه و تسک‌ها
- `README.md` — معرفی پروژه و روش اجرا
- `.env.example` — نمونه متغیرهای محیطی، بدون هیچ کلید واقعی
- `AGENTS.md` — قوانین کار Agentها
- `PROGRESS.md` — وضعیت اجرای تسک‌ها
- `DECISIONS.md` — تصمیم‌های معماری و دلیل آن‌ها

اگر ریپو هنوز خالی است، فقط یکی از اعضا اسکلت اولیه را بسازد و push کند؛ سپس عضو دوم pull بگیرد. از دو Agent نخواهید هم‌زمان فایل‌های پایه یا قراردادهای مشترک را تغییر دهند.

## ۲. روش پیشنهادی برای دو نفر

تقسیم کار پیشنهادی در این راهنما برای تیم دو نفره‌ای است که واقعاً روی پروژه کار می‌کنند. اگر نفر سوم هم وارد پیاده‌سازی شد، ابتدا مالکیت یک بخش مستقل به او بدهید.

- **OWNER=A — Data / Backend / Search:** واردسازی CSV، اعتبارسنجی داده‌ها، مدل داده، جست‌وجوی محصول، APIها، فیلترهای پرداخت و منطق فاصله.
- **OWNER=B — Frontend / UX / Journey:** رابط فارسی RTL، تجربه موبایل، کارت‌ها و مقایسه‌ها، فلوهای دستیار، وضعیت‌های خالی/خطا، پیام شبیه‌سازی‌شده و نمایش جایگزین‌ها.
- **Shared — Integration / Release:** قراردادهای API، تست سرتاسری، رفع ناسازگاری‌ها، دیپلوی و تمرین دمو. این بخش باید در هر تسک یک مالک مشخص داشته باشد؛ «مشترک» به معنی بدون مالک نیست.

این تقسیم با تسک‌های فایل اصلی هم‌پوشانی دارد؛ شناسه تسک‌ها را عوض نکنید. اگر یک تسک برای هر دو نفر لازم است، آن را به تسک‌های کوچک‌تر تبدیل کنید یا یکی را مالک و دیگری را reviewer تعیین کنید.

## ۳. شروع فقط با نفر A

1. یک ریپوی Git بسازید و فایل برنامه انگلیسی و این راهنما را در ریشه قرار دهید.
2. نفر A فایل‌ها را commit و push کند.
3. این پرامپت را به Agent بدهید:

> `Torob_InPerson_Shopping_Agent_Project_Plan_EN.md` منبع حقیقت تسک‌هاست. `TOROB_AGENT_WORKFLOW_GUIDE_FA.md` روش کار تیم را مشخص می‌کند. OWNER=A هستی. ابتدا ریپو، فایل‌ها و دیتاست موجود را بررسی کن. سپس فقط تسک‌های مربوط به Data / Backend / Search و زیرساخت پایه را انجام بده. قبل از تغییر قرارداد API، مدل داده یا فایل‌های مشترک، تصمیم را در `DECISIONS.md` ثبت کن و به مالک B اطلاع بده. تسک‌ها را یکی‌یکی اجرا کن، تست مربوطه را بنویس و اجرا کن، `PROGRESS.md` را به‌روزرسانی کن و هر مرحله قابل اجرا را commit کن. هیچ مدل پولی یا BoxAPI را صدا نزن. هیچ پیام یا تماس واقعی با فروشنده انجام نده.

4. Agent باید ابتدا ساختار ریپو و دیتاست را بررسی کند؛ نباید بدون بررسی، پروژه را از صفر بازنویسی کند.
5. پس از آماده شدن اسکلت، قراردادهای مشترک و تست‌های اولیه، push کنید. این نقطه را `SYNC-1` بنامید.

## ۴. شروع نفر B پس از `SYNC-1`

نفر B ابتدا این دستورات را اجرا کند:

```bash
git pull
git status
```

سپس به Agent بگوید:

> فایل `Torob_InPerson_Shopping_Agent_Project_Plan_EN.md` مرجع اصلی تسک‌هاست. `TOROB_AGENT_WORKFLOW_GUIDE_FA.md` قوانین هماهنگی تیم را مشخص می‌کند. OWNER=B هستی. ابتدا `AGENTS.md`، `PROGRESS.md`، `DECISIONS.md` و قراردادهای API را بخوان. فقط تسک‌های Frontend / UX / Journey را انجام بده. فرضیات مربوط به API را خودسرانه تغییر نده؛ اگر قراردادی کم است، آن را در `DECISIONS.md` ثبت کن و از OWNER=A تأیید بگیر. قبل از کار `git pull` و پس از تکمیل یک واحد کوچک و تست‌شده commit و push کن. هیچ مدل پولی، BoxAPI یا ارتباط واقعی با فروشنده را فعال نکن.

**نکته مهم:** A و B می‌توانند پس از `SYNC-1` موازی کار کنند، اما اگر هر دو یک فایل مشترک را تغییر دهند، احتمال conflict زیاد است. فایل‌های مشترک را مالک‌دار کنید و از تغییر هم‌زمان API schema، package config و routing خودداری کنید.

## ۵. حلقه اجرای تسک‌ها (Autopilot loop)

به Agent بگویید این چرخه را برای هر تسک تکرار کند:

1. `PROGRESS.md` و آخرین وضعیت Git را بخوان.
2. اولین تسک باز و بدون وابستگیِ متعلق به OWNER خودت را پیدا کن.
3. معیار پذیرش و وابستگی‌های آن تسک را از فایل برنامه بخوان.
4. قبل از کدنویسی، فایل‌های موجود و الگوهای پروژه را بررسی کن.
5. فقط همان تسک را پیاده‌سازی کن؛ از بازنویسی نامرتبط خودداری کن.
6. تست واحد/یکپارچه مربوط را اضافه و اجرا کن.
7. اگر تست شکست خورد، تا حد معقول علت را رفع کن؛ نتیجه را جعل نکن.
8. فایل `PROGRESS.md` را با وضعیت، فایل‌های تغییرکرده، تست‌ها، ریسک‌ها و قدم بعدی به‌روزرسانی کن.
9. اگر یک مرحله مستقل و سبز است، commit بساز. push را طبق سیاست تیم انجام بده.
10. به سراغ تسک بعدی برو، مگر اینکه نیاز به تصمیم انسانی، کلید/دسترسی، یا قرارداد مشترک باشد.

پرامپت ادامه پس از توقف:

> `Torob_InPerson_Shopping_Agent_Project_Plan_EN.md`، `AGENTS.md`، `PROGRESS.md` و `DECISIONS.md` را بخوان. تسک نیمه‌تمام را از روی کد و تست‌ها بررسی کن، از تکرار کار انجام‌شده خودداری کن و حلقه اجرای تسک‌های OWNER خودت را ادامه بده. اگر مسدود شدی، وضعیت و اقدام دقیق موردنیاز انسان را در `PROGRESS.md` ثبت کن.

## ۶. قالب وضعیت `PROGRESS.md`

از این وضعیت‌ها استفاده کنید:

- `TODO` — هنوز شروع نشده.
- `IN_PROGRESS` — در حال اجرا.
- `WAITING_HUMAN` — اقدام انسانی لازم است؛ دقیقاً بنویس چه کسی چه کاری انجام دهد.
- `BLOCKED` — وابستگی یا خطای حل‌نشده وجود دارد؛ دلیل و گزینه‌های رفع را ثبت کن.
- `REVIEW` — پیاده‌سازی انجام شده و منتظر بررسی نفر دیگر است.
- `DONE` — معیارهای پذیرش پاس شده و تست‌ها اجرا شده‌اند.

برای هر تسک ثبت شود: ID، عنوان، مالک، وضعیت، وابستگی‌ها، فایل‌های تغییرکرده، فرمان‌های تست و نتیجه، ریسک/محدودیت، قدم بعدی.

## ۷. قوانین حیاتی پروژه ترب

- قیمت `offers.csv` قیمت ثبت‌شده است؛ آن را قیمت لحظه‌ای یا قطعی معرفی نکن.
- وجود offer به معنی موجودی تأییدشده نیست.
- ساعات ثبت‌شده برنامه اعلامی فروشگاه‌اند، نه تضمین باز بودن لحظه‌ای.
- طبق توضیحات چالش، بیشتر نام فروشگاه‌ها ساختگی و همه شماره‌ها جعلی‌اند. شماره‌ای از دیتاست را برای تماس یا لینک واتس‌اپ واقعی استفاده نکن.
- ارتباط پیامکی/واتس‌اپ در نسخه دمو باید با برچسب واضح **«شبیه‌سازی؛ پیام واقعی ارسال نشده است»** نمایش داده شود.
- فیلتر خرید قسطی فقط باید فروشگاه‌هایی را نگه دارد که شواهد صریح در `payment_options` دارند. مقدار خالی یعنی «اطلاعات ثبت نشده»، نه «ندارد».
- اگر محصولی در دیتاست پیدا نشد، ادعا نکن در تهران وجود ندارد؛ پوشش دیتاست محدود است.
- هیچ کلید API یا رمز عبوری را commit نکن. مدل پولی به‌صورت پیش‌فرض غیرفعال بماند.

## ۸. کارهایی که انسان‌ها انجام می‌دهند

- انتخاب نهایی فناوری و تأیید تصمیم‌های معماری مهم.
- فراهم‌کردن دسترسی مخزن، دیتابیس و پلتفرم دیپلوی؛ کلیدها فقط در Secrets/Environment Variables.
- بررسی دستی خروجی فارسی و RTL روی موبایل واقعی.
- تأیید قانونی/فنی هر منبع خارجی و لینک عمومی.
- اجرای smoke test روی URL عملیاتی و بررسی لاگ‌ها.
- تمرین ارائه ۳ تا ۵ دقیقه‌ای و اطمینان از اینکه سناریوهای دمو تکرارپذیر هستند.
- تأیید نهایی هرگونه ارتباط واقعی با فروشنده؛ برای نسخه هکاتون، mock کافی است و امن‌تر است.

## ۹. پرامپت بازبینی نهایی

> فایل برنامه انگلیسی و `PROGRESS.md` را با کد واقعی مقایسه کن. فقط اعلام نکن که کار تمام شده؛ برای هر معیار پذیرش، شاهد قابل بررسی ارائه بده: فایل/مسیر، تست اجراشده و نتیجه. مواردی را که صرفاً mock هستند، واضح فهرست کن. مطمئن شو هیچ مدل پولی یا تماس واقعی فعال نیست، قیمت و موجودی اشتباه برچسب نخورده‌اند، فیلتر خرید قسطی محافظه‌کارانه است و مسیر اصلی روی نسخه deploy‌شده کار می‌کند. موارد ناقص را به‌صورت تسک‌های مشخص ثبت کن.

## ۱۰. ترتیب پیشنهادی برای رسیدن به دمو

1. داده وارد شود و جست‌وجوی محصول کار کند.
2. انتخاب محصول و مشاهده offerها کار کند.
3. فروشگاه‌ها بر اساس موقعیت/شعاع و قیمت قابل مقایسه باشند.
4. فیلتر قسطی و شفافیت اطلاعات درست باشند.
5. پیام شبیه‌سازی‌شده و مسیرهای جایگزین کار کنند.
6. UI فارسی و موبایل polish شود.
7. تست سرتاسری، دیپلوی و تمرین دمو انجام شود.

این ترتیب عمداً اول مسیر کامل و قابل داوری را می‌سازد؛ ویژگی‌های جذاب اما پرریسک مثل LLM واقعی و اتصال پیام‌رسان واقعی را به انتهای کار موکول می‌کند.
